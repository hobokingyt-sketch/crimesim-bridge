# BUILD-1: installed application acceptance

## Scope
The first Windows x64 development installer, not a game release. Use `delivery` module.
Rust is pinned by rust-toolchain.toml; Cargo.lock must be generated by Cargo and committed.
The official Tauri CLI 2.11.4 Windows archive is pinned by SHA-256 rather than rebuilt each run.
Godot remains at the existing 4.7.2 pin. A tool upgrade is a deliberate, tested change.

## Evidence chain
Checkout -> locked compile and real Godot E2E -> production recovery/worker tests ->
Tauri NSIS package -> fresh per-user installation -> actual installed frontend/IPC ->
bundled Godot initialize/update/export/launch/rollback/reapply/context pack -> reinstall ->
uninstall -> retained-data canary -> exact-installer SHA-256 manifest -> downloadable artifact.
Installer discovery uses cargo metadata target_directory, never a guessed src-tauri/target path.
Zero or multiple candidates fail; stale output is not selected by modification time.
PR runs now build and install a candidate as an acceptance test. This is not a public release.
No signing key or secret is provided to pull-request jobs. Normal CI uses read-only permissions.

## Native test mode
`crimesim-bridge.exe --bridge-install-check <new absolute directory>` is opt-in and developer-only.
It refuses existing directories and CRIMESIM_BRIDGE_* overrides. It never resets a normal workspace.
Normal startup follows the unchanged application flow. The real WebView must report that the
actual controls rendered through a Tauri command before the installed acceptance probe can run.
The probe calls the same project/update/coordinator/worker code, using an embedded test ZIP.
Godot must be installed from the application's bundled resources, with no source-tree runtime override.
A JSON report records exact source commit, executable, resource directory and accepted stages.
The Windows runner enforces a finite process deadline and saves diagnostics on failure.

## What this does not prove
This is a fresh application-directory install on a hosted Windows runner, not a pristine consumer PC
or an exhaustive click-by-click UI test. WebView2 may already be present; first-download failures are
not simulated. The installer retains its normal WebView2 bootstrapper behavior. A small save canary
checks the configured isolated data directory, not compatibility of future game save schemas.
The artifact is unsigned development software. Its hash detects changed bytes, not absence of bugs
or a Microsoft trust certificate. No code-signing or self-updater is delivered in this pass.
A packaging pass cannot substitute for the remaining SAFE-3/SAFE-4/SAFE-5/HEALTH-1 work.

## Failure and handoff
Only publish the verified-installer artifact after every required stage has succeeded. Report a
failed or still-running gate honestly. Do not call an artifact an installer merely because it is a
source ZIP. After acceptance, follow PACK-1 rather than adding mechanics to the Bridge repository.
The transient lock-bootstrap workflow is removed once its generated lock is retained on the branch.
